# 📌 ENTERPRISE DATA COMPILER — AI CODING CONTEXT PROMPT

---

## 🧠 PROJECT DEFINITION (IMPORTANT)

You are building an **Enterprise Data Compiler System**.

The system transforms messy enterprise data (CSV/Excel) into structured business models  using LLM-generated declarative Intermediate Representation (IR), a deterministic validation layer (Harness), and a native compiler runtime. 
AI DOES NOT write or execute raw Python code.

This system uniquely contains a **Layer 0 Matrix: An automated Control-Corrupted Chaos Engine & Mapping Benchmark Arena** to stress-test the defensive resilience of data pipelines.

This is NOT a chatbot, NOT an agent system.

It is a **data transformation compiler system equipped with an automated Chaos Engineering testing layer**.

---

## 🎯 CORE OBJECTIVE

Implement an end-to-end pipeline:

```text id="core_flow"
[Controlled Chaos Benchmarking Mode]
Layer 0: Chaos Engine (Injects Semantic Drift + Contract Violations + Human Noise)
     Produces: Mutated Messy CSV & Autogenerated Ontology Target

[Standard Pipeline Execution]
Layer 1: Connectors (Loads Raw CSV/Excel)
    ↓
Layer 2: Semantic Profiling Layer (Metadata + Fingerprints + Relationships)
    ↓  ← [Inject Mapping Registry History]
Layer 4: LLM Mapping Engine (generates structured IR JSON)
    ↓

    ↓

    ↓

    ↓
[Decision Router]
  ├── Confidence > 0.95 & Passed → Split Output: Clean Data (Layer 8)
  ├── Confidence > 0.80 & Failed → [Self-Healing Feedback Loop] → Back to Layer 4
  └── Confidence < 0.80 / Max Retries Reached → Quarantine for asynchronous review (Layer 7)
```

## ⚠️ IMPORTANT DESIGN CONSTRAINTS

1. AI MUST NOT directly modify database
2. AI MUST NOT generate executable programming code (Python/SQL). AI ONLY generates declarative Transformation IR specifications conforming to a strict JSON schema.
3. Execution must be entirely driven by white-listed, pre-defined native operators. No exec() or eval() mechanisms are permitted in the system.
4. All AI outputs MUST be validated by Harness before execution
5. System must be deterministic and auditable
6. No multi-agent system, no autonomous planning loops

## 🧱 SYSTEM ARCHITECTURE (8 LAYERS)

You MUST implement all layers as separate modules.

---

### LAYER 0 — DATA CHAOS & BENCHMARK MATRIX (THE MOAT)
Purpose: Generate deterministic, realistic data anomalies to test LLM semantic understanding and Layer 5 validation boundaries.
Mechanism: Two complementary modes of chaos generation:

1. **Atomic Corruptors** (for fine-grained robustness testing):
   - HeaderCorruptor: Column name drift (synonyms, case, prefixes, abbreviations)
   - HumanCorruptor: Typing errors (keyboard proximity, case, spaces, abbreviations with weights)
   - SpreadsheetCorruptor: Excel/CSV artifacts (serial dates, auto‑parsing, scientific notation, leading zero loss, boolean pollution)
   - MissingnessCorruptor: NULLs, empty strings, zero filling
   - ValueCorruptor: Field value synonyms (e.g., "Walk In" → "Walkin")
   - DependencyBreaker: Expression violations and date tolerance breaches

2. **Business Scenarios** (real-world data incidents):
   - Duplicate Import: Entire file duplicated (e.g., month‑end reconciliation error)
   - Month‑end Truncation: Export only first 80% of rows
   - Schema Evolution: Column additions, deletions, and renaming
   - Cross‑source Conflict: Value disagreements between POS and ERP
   - Delayed Reporting: Date shifts (e.g., 7 days late)
   - Aggregate Mismatch: Group totals inconsistent with line items

All corruptors and scenarios are unified under a single benchmark runner (`tests/run_robustness_benchmark.py`) that:
- Accepts clean data and automatically extracts target ontology (if not provided)
- Produces `(messy_df, ground_truth, corruption_log)`
- Executes the full 8‑layer compilation pipeline
- Computes IR accuracy (schema/operator scores), trust score, and (planned) per‑corruption detection/repair rates.

The **Mapping Benchmark Arena** tracks and compares IR generation accuracy across different LLM backends against the ground‑truth matrix.

### LAYER 1 — CONNECTORS
Purpose: Load raw enterprise data.
Support: CSV，Excel
Output: pandas DataFrame

### LAYER 2 — SEMANTIC PROFILER
Purpose: Analyze dataset structure, extract data fingerprints, and discover column relationships to eliminate semantic ambiguity.
Output schema profile JSON (Example):
{
  "fields": {
    "gross_sales": {
      "logical_type": "numeric",
      "null_ratio": 0.0,
      "fingerprint": {
        "min": 0.0,
        "max": 15000.0,
        "samples": [1050.0, 320.5]
      }
    },
    "tax_amount": {
      "relationships": [
        {"with": "gross_sales", "type": "linear", "formula": "x * 0.06"}
      ]
    }
  }
}

---
### LAYER 3 — SEMANTIC POLICY ENGINE & ONTOLOGY
Purpose: Define target structured business schema, ODCS (Open Data Contract Standard) constraints, and business-level semantics.
Structure: 
- Fields definitions (logical types)
- Semantic Policies (Fallback strategies for missing values like KEEP_NULL, USE_ZERO, HALT).
- ODCS Contracts (Complex mathematical expressions, volume conservation, and tolerance windows for asynchronous business delays).
*Also acts as the host for the Mapping Registry (Historical mapping memory).*

---

### LAYER 4 — LLM MAPPING ENGINE (CRITICAL)
Input: 
1. Semantic Profile (from Layer 2)
2. Target Ontology & ODCS Contracts (from Layer 3)
3. Historical Mapping Hints (from Mapping Registry)
Output: Strict Transformation IR (Intermediate Representation) JSON.  
- Must specify target fields, trusted operations (COPY, CONCAT, ADD, etc.), and typed input arguments (COLUMN_REF or LITERAL).
- Absolutely no code blocks or dynamic expressions allowed.

---

### LAYER 5 — DATA TRUST & CONTRACT ENGINE
This layer replaces the traditional validation harness.
- Phase 1 (Pre-check): IR Topology Validator (DAG cycle detection).
- Phase 2 (Post-check): Contract & Trust Engine. Evaluates the compiled DataFrame against Layer 3 policies. 
- Features: Generates a Trust Score based on mapping confidence, data integrity, and dataset-level assertions (e.g., Sum Alignment). Determines whether to pass, auto-heal, or quarantine data.

---

### LAYER 6 — DETERMINISTIC COMPILER RUNTIME & CANONICALIZER
Purpose: Safely compile and execute the validated IR, whilst handling formatting chaos natively.
- Mechanism: Translates declarative IR instructions into native Pandas operations.
- Canonicalization: Includes high-level operators (e.g., PARSE_DATE, CLEAN_CURRENCY, FUZZY_MAP) to standardize formats (ISO8601, Numeric) before complex math operations.
- Error Handling: Handles computational exceptions gracefully via vector type coercion.

---

### LAYER 7 — HUMAN REVIEW MODULE

Purpose: Manage anomalies through autonomous remediation (MAPE-K loop).
- Mechanism: Extracts failing rule IDs and messy data samples from the Data Trust Engine (Layer 5).
- Feedback Loop: Packages the failure context and prompts the LLM Mapping Engine (Layer 4) for an incremental topology patch.
- Human Review: Only triggered when max automated retries are exhausted or data suffers critical systemic collapse.

Output:
* mapping result
* validation report
* execution summary

Allow:
* approve
* reject
* modify rules

---

### LAYER 8 — OUTPUT LAYER
Write clean structured data to:
* SQLite database (primary)
* CSV export (secondary)

## 🔁 END-TO-END PIPELINE RULE

The system MUST implement a single orchestrator:

```text
run_benchmark():
    trigger Layer 0 to generate messy payload and target ontology
    pass payload to run_pipeline()

run_pipeline(input_file, target_ontology, max_retries=2):
    load raw data (Layer 1)
    profile semantic attributes (Layer 2)
    
    for attempt in 0 to max_retries:
        call LLM engine to generate/patch IR Specification (Layer 4)
        validate IR topology (Layer 5 Phase 1)
        compile and canonicalize data (Layer 6)
        evaluate Trust Score and enforce ODCS (Layer 5 Phase 2)
        
        if passed and high_confidence → write to DB (Layer 8) and exit
        if failed and attempt < max_retries → extract messy samples, loop back to Layer 4
        
    route unhealable anomalous records to Quarantine DB (Layer 7)
```
