## 🧠 PROJECT DEFINITION (IMPORTANT)

You are building an **Enterprise Data Compiler System**.

The system transforms messy enterprise data (CSV/Excel) into structured business models  using LLM-generated declarative Intermediate Representation (IR), a deterministic validation layer (Harness), and a native compiler runtime. 
AI DOES NOT write or execute raw Python code.

This system uniquely contains a **Layer 0 Matrix: An automated Control-Corrupted Chaos Engine & Mapping Benchmark Arena** to stress-test the defensive resilience of data pipelines.

This is NOT a chatbot, NOT an agent system.

It is a **data transformation compiler system equipped with an automated Chaos Engineering testing layer**.

## ⚠️ IMPORTANT DESIGN CONSTRAINTS

1. AI MUST NOT directly modify database
2. AI MUST NOT generate executable programming code (Python/SQL). AI ONLY generates declarative Transformation IR specifications conforming to a strict JSON schema.
3. Execution must be entirely driven by white-listed, pre-defined native operators. No exec() or eval() mechanisms are permitted in the system.
4. All AI outputs MUST be validated by Harness before execution
5. System must be deterministic and auditable
6. No multi-agent system, no autonomous planning loops
7. BOUNDED AI AUTHORITY: The LLM is strictly a Copilot. It CANNOT autonomously trigger a pipeline re-run with modified rules. It can only propose a `DRAFT` MappingSpec.
8. IMMUTABILITY OF EFFECT: Once data hits Layer 8, rollback is achieved strictly via Saga Compensation (Inverse IR generation), never via physical SQL DELETE.
9. STATE MACHINE ENFORCEMENT: Pipeline execution must strictly follow the Batch State lifecycle: INIT -> PROFILED -> COMPILED -> RECONCILED -> COMMITTED | QUARANTINED.

## 🧱 SYSTEM ARCHITECTURE (8 LAYERS)

You MUST implement all layers as separate modules.

---

### LAYER 1 — CONNECTORS
Purpose: Load raw enterprise data.
Support: CSV，Excel
Output: pandas DataFrame

---

### LAYER 2 — SEMANTIC PROFILER
Purpose: Analyze dataset structure, extract data fingerprints, and discover column relationships to eliminate semantic ambiguity.
Output schema profile JSON (Example):
{
  "fields": {
    "gross_sales": {
      "logical_type": "numeric",
      "null_ratio": 0.0,
      "fingerprint": {
        "min": 0.0,
        "max": 15000.0,
        "samples": [1050.0, 320.5]
      }
    },
    "tax_amount": {
      "relationships": [
        {"with": "gross_sales", "type": "linear", "formula": "x * 0.06"}
      ]
    }
  }
}

---

### LAYER 2.5 — SCHEMA INTROSPECTION (BRIDGE TO DOWNSTREAM SYSTEMS)
Purpose: Dynamically discover the output schema of a target ERP/accounting system (SAP, AutoCount, Oracle, POS, etc.).
Mechanism: Connects to the system’s database or API, reads table structures, column names, data types, primary/foreign keys, and constraints.
Output: Vendor Schema Graph – a machine‑readable representation of the system’s expected data structure.
This graph is then used by Layer 3 Adapters to produce mapping hints and validate the final output.

---
### LAYER 3 — SEMANTIC POLICY ENGINE & ONTOLOGY & ADAPTERS

**Purpose**: Provide semantic grounding for the compiler. Separates stable business concepts from system-specific target structures.

**Canonical Ontology** (stable semantic layer):
- Defines cross‑ERP business entities (e.g., `BusinessPartner`, `Product`, `CommercialDocument`, `JournalEntry`).
- Acts as the **coordinate system** for all mapping and evaluation.
- Human‑maintained JSON file (`canonical_ontology.json`).

**Target Ontology** (system‑specific output schema):
- Represents the exact structure expected by a downstream ERP (SAP, AutoCount, POS, etc.).
- **Discovered dynamically** via **Schema Introspection** (reading tables/fields/types/constraints from the target system).
- Contains fields, types, ODCS contracts (row‑level & global invariants), and fallback policies.

**Adapter** (per‑system mapping component):
- One adapter per downstream system (e.g., `SAPAdapter`, `AutoCountAdapter`).
- Provides:
  - `introspect_schema()` → returns Vendor Schema Graph.
  - `mapping_hints` (source → canonical field) – manually curated or LLM‑assisted.
- Enables LLM to generate IR even when hints are incomplete (semantic inference on values).

**Mapping Registry**: Historical mapping memory (optional, domain‑specific).

---

### LAYER 4 — LLM MAPPING ENGINE (CRITICAL)
Input: 
1. Semantic Profile (from Layer 2)
2. Canonical Ontology (from Layer 3) – defines the semantic coordinate space.
3. Target Ontology (optional) – if provided, the final IR must conform to it; otherwise, IR targets the Canonical Ontology.
4. Adapter Mapping Hints (source → canonical) – from the corresponding system adapter.
5. Historical Mapping Hints (from Mapping Registry – optional).
Output: A version-controlled `MappingSpec` JSON entity.
- The output MUST encapsulate the Transformation IR inside a Spec wrapper with a `DRAFT` status.
- The AI acts purely as a semantic reasoning engine to propose mappings, without execution privileges.

---

### LAYER 5 — DATA TRUST & CONTRACT ENGINE
This layer replaces the traditional validation harness.
- Phase 1 (Pre-check): IR Topology Validator (DAG cycle detection).
- Phase 2 (Post-check): Contract & Trust Engine. Evaluates the compiled DataFrame against Layer 3 policies. 
- Features: Generates a Trust Score based on mapping confidence, data integrity, and dataset-level assertions (e.g., Sum Alignment). Determines whether to pass, auto-heal, or quarantine data.

---

### LAYER 6 — DETERMINISTIC COMPILER RUNTIME & CANONICALIZER
Purpose: Safely compile and execute the validated IR, whilst handling formatting chaos natively.
- Mechanism: Translates declarative IR instructions into native Pandas operations.
- Canonicalization: Includes high-level operators (e.g., PARSE_DATE, CLEAN_CURRENCY, FUZZY_MAP) to standardize formats (ISO8601, Numeric) before complex math operations.
- Error Handling: Handles computational exceptions gracefully via vector type coercion.

---

### LAYER 7 — HUMAN REVIEW MODULE
Purpose: Handle complex business states, external accounting reality, and failure recovery.
- Reconciliation: Enforces global invariants such as Double-Entry balancing (Debit == Credit) and Payment Date tolerances (e.g., accepting a 3-day drift between payment and posting dates).
- Saga Compensation: If Layer 8 encounters a network crash or database lock leading to a partial commit, this module invokes an `InverseCompiler`. 
  It dynamically calculates the inverse of the transformation graph to generate Red-ink (Reversal) data to offset the corrupted state in the ERP.

---

### LAYER 8 — OUTPUT LAYER
Write clean structured data to:
* SQLite database (primary)
* CSV export (secondary)

## 🔁 END-TO-END PIPELINE RULE

The system MUST implement a single orchestrator:

```text
run_benchmark():
    trigger Layer 0 to generate messy payload and target ontology
    pass payload to run_pipeline()

run_pipeline(source_data, active_spec, target_ontology):
    Assert active_spec.status == "LOCKED" (Halt if DRAFT)
    
    Update Batch State -> INIT
    Profile semantic attributes (Layer 2)
    
    Update Batch State -> COMPILED
    Validate IR topology (Layer 5-P1)
    compiled_df = Execute Deterministic Compiler (Layer 6)
    
    Update Batch State -> RECONCILED
    audit_report = Evaluate Trust Score, ODCS, and Global Invariants (Layer 5-P2 & Layer 7)
    
    if audit_report.routing_decision == "PASS":
        try:
            Update Batch State -> COMMITTING
            Write to DB (Layer 8)
            Update Batch State -> COMMITTED
        except CommitFailure:
            Execute Saga Compensation (Layer 7)
            Update Batch State -> QUARANTINED
    else:
        Route failed records to Quarantine DB
        Trigger LLM (Layer 4) to propose asynchronous DRAFT patch based on failure signatures
        Update Batch State -> QUARANTINED
```

### DATA CHAOS & BENCHMARK MATRIX (THE MOAT)
Purpose: Generate deterministic, realistic data anomalies to test LLM semantic understanding and Layer 5 validation boundaries.
Mechanism: Two complementary modes of chaos generation:

1. **Atomic Corruptors** (for fine-grained robustness testing):
   - HeaderCorruptor: Column name drift (synonyms, case, prefixes, abbreviations)
   - HumanCorruptor: Typing errors (keyboard proximity, case, spaces, abbreviations with weights)
   - SpreadsheetCorruptor: Excel/CSV artifacts (serial dates, auto‑parsing, scientific notation, leading zero loss, boolean pollution)
   - MissingnessCorruptor: NULLs, empty strings, zero filling
   - ValueCorruptor: Field value synonyms (e.g., "Walk In" → "Walkin")
   - DependencyBreaker: Expression violations and date tolerance breaches

2. **Business Scenarios** (real-world data incidents):
   - Duplicate Import: Entire file duplicated (e.g., month‑end reconciliation error)
   - Month‑end Truncation: Export only first 80% of rows
   - Schema Evolution: Column additions, deletions, and renaming
   - Cross‑source Conflict: Value disagreements between POS and ERP
   - Delayed Reporting: Date shifts (e.g., 7 days late)
   - Aggregate Mismatch: Group totals inconsistent with line items

All corruptors and scenarios are unified under a single benchmark runner (`tests/run_robustness_benchmark.py`) that:
- Accepts clean data and automatically extracts target ontology (if not provided)
- Produces `(messy_df, ground_truth, corruption_log)`
- Executes the full 8‑layer compilation pipeline
- Computes IR accuracy (schema/operator scores), trust score, and (planned) per‑corruption detection/repair rates.

The **Mapping Benchmark Arena** tracks and compares IR generation accuracy across different LLM backends against the ground‑truth matrix.

## 🧠 CORE DESIGN PRINCIPLE

This system is NOT:
* A multi-agent autonomous system
* A chatbot or conversational UI
* An ETL script with in-place data mutation

It IS:
> **A stateful semantic compiler operating under enterprise-controlled execution semantics.**

**Three Core Pillars:**
1. **Control Plane (Governance):** LLM acts ONLY as a "Proposer" (Bounded AI Role). It generates declarative `MappingSpec` drafts. Human experts must review and transition the spec to a `LOCKED` state before execution.
2. **Compilation Plane (Pure Function):** A completely stateless, deterministic execution engine (Layer 6) that safely applies the `LOCKED` IR graph to the messy data in memory.
3. **Execution Plane (Physical Reality & Saga):** A state-machine-driven environment handling external side-effects (database commits). If a partial failure occurs during database write, the system MUST NOT perform a physical `DELETE`. Instead, it triggers a **Saga Compensation Pattern**, generating an Inverse IR to write negative/reversal journal entries (Red-ink adjustment).
