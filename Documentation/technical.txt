=============== 01 ==================

经过对项目代码的**完整审视**，并从**“真实数据迁移/标准化落地场景”**出发，我找出了以下 **12个关键的功能性缺口**。这些缺口并非代码Bug，而是**架构层面的待完善点**，它们直接决定了你的原型能否在客户面前证明“工业价值、可扩展性和可落地性”。

[DONE]
## 1. **缺乏“目标系统Schema自动发现”能力**（致命缺口）
- **现状**：`ontology_registry.json` 是手写的静态文件。
- **真实场景**：对接SAP或AutoCount时，需要连接数据库或API，自动读取表结构、字段类型、主外键、约束，并生成`TargetOntology`。
- **影响**：无法展示“适配不同ERP”的自动化能力，被视为“硬编码模板”。
- **最小修补建议**：在`main.py`增加`--introspect`模式，调用一个虚拟的`SchemaIntrospector`（可从SQLite读取表结构）生成JSON，证明可动态生成。

---

[DONE]
## 2. **LLM生成的IR缺少对“复杂关联”的验证**（逻辑缺口）
- **现状**：`IRValidator`检查DAG和算子选项，但**没有验证输出字段是否满足目标表的业务唯一键、外键约束**。
- **真实场景**：目标表有联合主键（如`document_id + line_id`），LLM可能生成缺少部分字段的映射。
- **影响**：无法保证最终数据能成功写入目标系统。
- **修补建议**：在`IRValidator`中加入对`target_ontology`中`unique`、`foreign_key`约束的静态检查（即使不执行，也要检查输出映射是否覆盖这些字段）。

---

[DONE]
## 3. **缺少“增量更新”与“历史变更追踪”机制**（运维缺口）
- **现状**：全量覆盖写入，无`upsert`或`merge`逻辑。
- **真实场景**：每日增量迁移，需根据主键更新或插入。
- **影响**：无法用于生产迁移，只能做一次性全量。
- **修补建议**：在`SQLiteWriter`中增加`upsert`逻辑（基于主键），并让`TargetOntology`支持指定`primary_key`字段，展示增量能力。

---

[DONE]
## 4. **数据质量规则（ODCS）无法自动生成**（智能缺口）
- **现状**：规则必须人工编写到JSON。
- **真实场景**：从目标系统的约束（如`NOT NULL`、`CHECK`）自动推导出`RowLevelRule`。
- **影响**：LLM能生成映射，但规则仍需人工，降低了自动化程度。
- **修补建议**：在`SchemaIntrospector`中增加规则生成函数，将数据库约束自动转成ODCS规则，注入`TargetOntology`。

---

[DONE]
## 5. **缺少“映射失败时自动生成DRAFT补丁”的闭环**（自治缺口）
- **现状**：`orchestrator.py`中有注释“通知SemanticMapper生成DRAFT补丁”，但并未实现。
- **真实场景**：批次被隔离后，系统应自动分析错误并提议修正的Spec，形成闭环。
- **影响**：无法展示“自我进化”能力，人工介入成本高。
- **修补建议**：在`orchestrator.py`的`else`分支中，调用`SemanticMapper.generate_spec`，传入`_extract_failure_context`的结果，生成新`DRAFT`并保存到`SpecRepository`。

---

[DONE]
## 6. **缺少“多源数据融合”能力**（集成缺口）
- **现状**：单表输入（CSV），无多源JOIN。
- **真实场景**：迁移常需合并多个源表（如订单头+行）。
- **影响**：无法应对复杂数据结构。
- **修补建议**：在`WaveOrchestrator`中允许一个任务引用多个源数据集（通过`source_dataset_key`列表），并在`PipelineOrchestrator`中支持`JOIN`算子作为第一步。

---

## 7. **缺少“数据预览与抽样”交互**（用户体验缺口）
- **现状**：全量处理，无提前预览映射效果。
- **真实场景**：客户希望在迁移前看到映射样例结果。
- **影响**：缺乏信心，无法早期发现问题。
- **修补建议**：在`main.py`增加`--preview`参数，仅处理前100行并输出映射后的前5行和审计摘要。

---

[DONE]
## 8. **缺少“回滚策略”的可视化**（操作缺口）
- **现状**：Saga冲销逻辑存在，但无界面展示冲销记录。
- **真实场景**：审计人员需要查看冲销凭证。
- **影响**：Saga价值无法被直观感知。
- **修补建议**：在`QuarantineViewer`输出中加入`reversal_records`字段，展示生成的红字数据。

---

## 9. **LLM提示词缺少“业务上下文”**（语义缺口）
- **现状**：提示词只有列名和类型，无业务含义。
- **真实场景**：列名如`CUSTNO`，需解释为“客户编号”。
- **影响**：映射准确率低。
- **修补建议**：在`SemanticProfiler`中增加基于外部术语库（或LLM自身知识）的列名解析，生成`business_meaning`字段注入到`source_schema`。

---

[DONE]
## 10. **缺少“映射历史版本对比”功能**（治理缺口）
- **现状**：`SpecRepository`可存储多版本，但无对比。
- **真实场景**：需展示变更影响范围。
- **影响**：难以管理演进。
- **修补建议**：在`governor.py`增加`diff_specs(spec1, spec2)`方法，输出IR差异。

---

## 11. **对“半结构化数据”支持不足**（格式缺口）
- **现状**：只处理扁平表，无JSON/XML解析。
- **真实场景**：很多系统导出JSON格式。
- **影响**：限制数据源类型。
- **修补建议**：在`connectors`中增加`JSONConnector`，能将嵌套结构展开为DataFrame（使用`json_normalize`）。

---

## 12. **缺少“性能基准测试”工具**（论证缺口）
- **现状**：无压力测试。
- **真实场景**：客户要求吞吐量数据。
- **影响**：无法证明可扩展性。
- **修补建议**：写一个脚本用`pytest-benchmark`测试不同数据量（1k、10k、100k）的编译时间，展示接近O(n)的线性扩展。

---

## 总结：如何用最小改动快速证明价值

为在客户面前展示“工业级潜力”，建议优先修补以下 **4个关键缺口**（按重要性排序）：

1. **自动Schema Introspection**（第1项）—— 证明适配不同系统。
2. **失败补丁自动生成闭环**（第5项）—— 证明自治能力。
3. **增量更新支持**（第3项）—— 证明适合生产迁移。
4. **多源JOIN能力**（第6项）—— 证明处理复杂场景。

这些修改均在`prototype`能力范围内，且不改变现有核心架构。完成这些后，你的原型将具备**企业级POC的敲门砖**，远超普通ETL工具。

## 四、推荐升级方案（分阶段）

我们不必一次性重写，而是分两步走：

### 第一阶段（当前版本）—— 轻微扩展（保持轻量）

在现有 `canonical_ontology.json` 中增加两个轻量级结构：

1. **Relationships**（在 `odcs_contracts` 同级或新建 `relationships` 数组）
2. **Cross-entity rules**（扩充 `global_invariants` 类型）

这样改动量极小，且不影响现有流水线。

#### 示例补充（仅增加必要项）：

```json
{
  "relationships": [
    { "from": "CommercialDocument", "to": "CommercialDocumentLine", "cardinality": "1:N", "via": "document_id" },
    { "from": "BusinessPartner", "to": "CommercialDocument", "cardinality": "1:N", "via": "partner_id" }
  ],
  "odcs_contracts": {
    "global_invariants": [
      // 现有保持不变
    ],
    "cross_entity_rules": [  // 新增一个数组
      {
        "name": "invoice_must_have_lines",
        "type": "existence_check",
        "source_entity": "CommercialDocument",
        "target_entity": "CommercialDocumentLine",
        "foreign_key": "document_id",
        "severity": "error"
      }
    ]
  }
}
```

### 第二阶段（下一步）—— 接入真实 ERP 时补充

当我们要集成 SAP 或 AutoCount 时，需要：

- 在 `TargetSchemaIntrospector` 中识别外键关系，填充 `relationships`。
- 在 `IRValidator` 中增加对这些关系的静态校验。
- 在 `DataTrustEngine` 或 `ReconciliationEngine` 中实现 `cross_entity_rules` 的检查。

这个阶段才是真正的“语义图谱”建设。

## 五、对现有代码的改动（最小实现）

如果我们决定立即实施第一阶段的升级，那么需要修改以下文件：

1. **`app/ontology/business_schema.py`**  
   - 在 `TargetOntology` 模型中增加 `relationships` 和 `cross_entity_rules` 字段（可选，可放在 `odcs_contracts` 内或平级）。
   - 在 `_merge_rules` 中合并 `relationships` 和 `cross_entity_rules`。

3. **`app/harness/ir_validator.py`**  
   - 在 `validate_topology` 中增加对外键关系的静态检查（确保 `output_mappings` 包含关联字段）。
