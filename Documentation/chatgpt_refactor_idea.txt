# 我还想补充一个我认为可以进一步优化的地方（之前我们还没讨论到）

我建议再增加一个**Rule & Feedback Layer**，放在 IR-2 和 IR-3 之间。

原因是企业迁移几乎都会有人工审核。例如：

* LLM 推断 `client_code` 是 `Customer ID`，顾问改成 `Business Partner ID`。
* 某个 FK 被误判，人工修正。
* 某个实体被拆分或合并。

这些修正**不要只修改最终 Mapping**，而应该回写成规则，进入一个可复用的知识库：

```text
Human Review
      │
      ▼
Rule Repository
      │
      ▼
下一次项目优先应用这些规则
```

这样 EDC 会随着项目越来越"懂企业数据"，而不是每次都从零开始推理。

# 最终定位

经过我们这几轮讨论，我认为 EDC 的定位已经可以明确为：

> **一个以多层 Intermediate Representation（IR）为核心、以 Evidence Graph 为推理基础、利用 LLM 完成企业语义重建（Enterprise Semantic Reconstruction），最终编译为可执行 ERP Migration Pipeline 的 Enterprise Data Compiler。**

它不是传统 ETL 工具，也不是简单的 AI Mapping 工具，而是把**数据事实（Facts）→ 证据（Evidence）→ 业务语义（Semantics）→ 迁移执行（Execution）**明确拆分成多个可解释、可审计、可人工介入的编译阶段。这一点，也是我认为它最有研究价值和工程价值的地方。

# 不过，我还想提出一个我认为更值得深入思考的问题

你目前把 **Resolution** 放在一个阶段，但实际上它会形成一个**循环（Iterative Loop）**。

举个例子：

第一轮：

LLM：

认为：

```text
IBM

IBM Corp
```

不是同一个。

后来：

发现：

Tax Number：

一样。

Address：

一样。

Phone：

一样。

于是：

Resolution：

更新。

Evidence：

改变。

Entity：

改变。

ERD：

可能：

也改变。

所以：

整个系统：

其实应该：

不是：

```text
Phase1

↓

Phase2

↓

Phase3
```

而是：

```text
Evidence Graph

↓

Semantic Reasoning

↓

Resolution

↓

Evidence 更新

↓

Semantic Reasoning

↓

...

直到收敛（Convergence）
```

也就是说，**Entity Discovery、Relationship Discovery 和 Resolution 不应该是一次性的，而应该共同优化（joint optimization）**。这是数据库领域、知识图谱（Knowledge Graph）和 Entity Resolution 系统中比较常见的思路。

如果未来你的 EDC 要做到研究级甚至接近产品级，我认为这会比继续堆更多 LLM Prompt 更值得投入。因为企业数据理解本质上不是一次推理，而是一个不断积累证据、修正假设、直到语义模型稳定的过程。
